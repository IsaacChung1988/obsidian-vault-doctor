# Obsidian Restructure Planner

本 Skill 是**决策层**：它不扫库、不动文件，只回答一个问题——

> **诊断结果有三十条，我到底先干哪个？**

底层能力由兄弟 skill `obsidian-vault-engine` 提供（同一专家包内已内嵌）。
分工不可混淆：

| 层 | 谁做 | 回答什么 |
|---|---|---|
| 看见 | `engine/scan.py` | 库里有什么 |
| 判断 | `engine/health.py` / `engine/dup.py` | 有什么毛病、像不像重复 |
| **决策** | **本 skill 的 `plan.py`** | **先做什么、做完能好多少** |
| 动手 | `engine/move.py` | 安全地搬 / 改名 / 回滚 |

---

## 0. 硬规则（每次任务开始前必读）

1. **本 skill 全程只读。** `plan.py` 不改任何文件，它产出的是计划。任何写操作一律交给 `engine/move.py`，并遵守引擎的备份与回滚规则。
2. **不许跳过 scan 直接执行。** 没有 `index.json` 就没有计划；没有计划就不许动手。
3. **不许把 C 级项报成问题。** 模板占位断链、日记无入链、归档缺元数据、同名异内容——这些在每一个 Obsidian 库里都是常态。把它们说成"你的库有问题"是**在骗用户**，也是让工具显得不懂 Obsidian 的最快方式。
4. **健康分只能用来对比前后，不许横向比较。** 用户问"我这库 64 分算好吗"，如实回答：这个分数是我定的口径（见 §3），只能说明你这个库自己的问题有多集中，不能说明你的库比别人差。
5. **不替用户决定 B 级项。** B 级的定义就是"没有标准答案"，你可以给建议，但必须由用户拍板。

---

## 1. 运行环境与依赖

- Python 3.8+，**纯标准库**，不需要 `pip install` 任何东西。
- 依赖同包内的引擎脚本：
  ```
  <专家包>/skills/engine/scripts/scan.py     ← 必须存在
  <专家包>/skills/engine/scripts/dup.py      ← 可选（缺了就没有近似重复一项）
  <专家包>/skills/planner/scripts/plan.py    ← 本 skill
  ```
- 若引擎目录缺失，**如实告知用户"这个专家包不完整，请重新安装"**，不要试图自己重写扫描逻辑。

---

## 2. 标准流程

```bash
# ① 定位库（多库时交用户选，不替用户挑）
python3 engine/scripts/vault.py --auto

# ② 扫描（只读，产出基线）
python3 engine/scripts/scan.py "$VAULT" -o index.json

# ③ 算相似度（只读，为 B 级里的「相似笔记」提供依据）
python3 engine/scripts/dup.py index.json --json dup.json

# ④ 出治理计划（只读，本 skill 的核心）
python3 planner/scripts/plan.py index.json --dup dup.json -o plan.md
```

**给用户的第一话**：直接给 `plan.py` 的终端输出，不要先念一遍 scan 的战报。
用户不关心"我扫了 319 个文件"，只关心"我该怎么办"。

## 3. 分级口径（这是产品的核心判断，写死不许临场改）

### A 级 · 立刻能修

标准：**有唯一正确答案**。修完不会后悔，不需要用户判断。

| 项 | 为什么算 A 级 | 风险 |
|---|---|---|
| 系统垃圾文件（`.DS_Store` / `Thumbs.db` / `._*`） | Obsidian 自己不认，删了不影响任何笔记 | 零 |
| 字节级完全重复的笔记 | 内容一模一样，合并后一个字都不丢 | 零 |
| 同名且内容一致的笔记 | 留一份就够 | 零 |
| 正文断链 | 每条都有明确目标，不是猜 | 低（要人确认改到哪） |

### B 级 · 要你判断

标准：**没有标准答案**，取决于用户怎么用这个库。

| 项 | 为什么必须人来定 |
|---|---|
| 高度相似笔记（≥0.95） | 可能是同一篇的两个版本，也可能是"正式版 + 存档版"都想要 |
| 中度相似（0.85–0.95） | 多半是同一主题的不同侧面，合并会丢信息 |
| 低度相似（0.70–0.85） | 只列出，不建议动 |
| 没人链接的笔记（孤儿） | 要么链进索引，要么归档——但"该留还是该归档"只有用户知道 |
| 缺 frontmatter | 补什么字段、补到什么程度，取决于用户用不用 Dataview |

### C 级 · 不要动

标准：**看着像问题，其实是常态**。动了反而坏。

| 现象 | 为什么不是病 |
|---|---|
| 模板里的 `[[示例名]]` 断链 | 占位符，等着被填 |
| 日记无入链 | 按日期命名，天生没人回链 |
| 索引页 / MOC 无入链 | 它是链接的起点，不需要被链 |
| 归档无入链 | 留存副本，不参与链接网络 |
| 归档 / 模板缺 frontmatter | 快照和骨架，不算笔记 |
| 同名但内容不同 | 分类设计（各项目目录下各一份「项目卡」），合并就错了 |

> **这一档是产品质量的分水岭。** 不懂行的工具会把这 6 类全报成问题，用户看到的是"满屏红色"，然后关掉窗口再也不打开。

## 4. 健康分口径

四项加权，从 100 分里扣，每项有「扣满临界点」：

| 项 | 权重 | 扣满条件 |
|---|---|---|
| 断链率 | 30 | 链接的 15% 断掉 |
| 孤儿率 | 25 | 正文的 60% 无入链 |
| 重复率 | 25 | 正文的 30% 是重复 |
| 缺元数据率 | 20 | 笔记的 70% 无 frontmatter |

分母设下限（链接至少按 20 条、正文至少按 10 篇算），避免小库被单条问题放大。
正文不足 20 篇时，输出会带「样本太小，分数参考意义有限」的提示——**不要省略这个提示**。

**上报时的固定说法**：
> 这个分数是我定的口径，不是行业标准。它只用来对比你治理前后有没有变好。

---

## 5. 迁移协议（要动文件时怎么走）

`plan.py` 只出计划。执行必须按下面顺序，一步都不能跳：

1. **确认在 A 级范围内。** B 级项不许批量执行。
2. **提示关闭 Obsidian。** 运行中的 watcher 会缓存目录状态，边改边看会产生编辑冲突。
3. **让引擎生成备份。** `move.py` 自动产出 `affected.zip` + `change-log.csv`，**缺一不可**。
4. **执行后立刻 verify。** 结构级差异应为 0；不为 0 就停下来说清楚差异是什么。
5. **告诉用户回滚命令。** 不说回滚方式的变更，等于没做完。

**禁止**：`rm`、清空 `.trash`、手动改 `.obsidian/`。唯一允许的"删除"是移入库内 `.trash/`（可回滚）。

## 6. 边界与降级（不确定时必须这么说）

| 情况 | 正确做法 |
|---|---|
| 没给 `dup.json` | 明确说"近似重复这项没检测，不代表没有"，并给出补跑命令。**不许默认 0** |
| 用户库全是日记 / 时间流 | 说"你的库以时间流为主，孤儿指标对你意义不大"，改看断链和模板 |
| 用户库 < 20 篇 | 说"库还小，健康分参考意义有限"，直接给清单，别拿分数吓人 |
| 用户想一次治理 200 篇 | 拦住。建议按目录分批，每批 ≤ 50，每批做完 verify 再下一批 |
| 用户要求"全自动整理好" | 拒绝。B 级项没有正确答案，全自动 = 替用户做决定。最多做到 A 级全自动 + B 级出提案 |
| 引擎脚本缺失 | 如实说包不完整，不要用通用知识糊弄 |

---

## 7. 结果呈现

终端给**人话版**（`plan.py` 默认输出），文件给**完整版**（`-o plan.md`）。

给用户讲的时候，顺序固定：
1. 你的库多大（一句话）
2. 健康分多少（一句话 + 口径说明）
3. A 级几项、做完能涨多少分（这是用户最想听的）
4. B 级几项、需要他拍板什么
5. C 级为什么不用管（简短带过，不要展开）
6. 建议顺序

**不要**把 C 级放在前面解释一大堆——用户会觉得你在为"没查出问题"辩解。
